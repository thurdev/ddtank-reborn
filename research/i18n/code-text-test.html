Code-driven "erase + render PT-BR text" quality test

4 images, one of each kind, run through a fresh pixel-measured pipeline (tools/i18n/images/_code-test-measure.mjs + tools/i18n/images/_code-text-test-render.mjs) — not the existing tools/i18n/images/replace.mjs, which was judged ugly (wrong fonts, bad erasing, OCR noise) and was only read for reference. Text boxes/colors here come from direct pixel measurement, not OCR, to rule out OCR noise as a variable. Originals are shown at their native size; results are upscaled 2x with nearest-neighbour so individual pixels/antialiasing are visible.

1. Panel tooltip (plain flat text) — AgreeProposeAsset

Font: system Arial (not the FFDec-extracted core.swf Arial — see finding below).
Method: pixel-scanned bbox restricted to y≥75 (below the heart garland) found two lines, right-edge-aligned (x1 within 7px of each other across lines) → rendered right-aligned. Fill/outline sampled as near-black, flat (no outline/stroke). Backdrop opaque (pink, ~a=255) → erased via alpha dest-out then refilled with a 2-stop vertical gradient sampled from the strips just above/below the box.
Ink-density sanity check: orig 4.0% of region, result 8.1% (longer PT-BR string, expected).
Verdict: Good. Clean erase (no Vietnamese fragments, no visible patch seam), weight/size close to the original, alignment preserved.

2. Chunky gradient/outlined title — "Bảng phần thưởng" → "Tabela de recompensas"

Font: Lilita One (bundled OFL, images/fonts/LilitaOne.ttf) — no embedded TTF exists for this one: the title is baked straight into the bitmap art, not an SWF text field, so there was nothing to extract; Lilita One was picked by eye as the closest bundled match to the rounded, condensed, heavy-weight look.
Method: bbox = whole non-near-white region (single line, nearly full width). Fill = measured light-orange→darker-orange 2-stop gradient, outline = measured dark brown-red, plus a drop shadow — all reproduced with the faux-outline/gradient/shadow renderer. Backdrop measured as transparent (title PNG has no opaque background despite looking white in a browser preview) → erase only, no fill patch needed.
Ink-density sanity check: orig 26% of region, result 40% (PT-BR string is longer, font auto-fit chose a slightly smaller size — 30px vs the box's 48px height — to keep it on one line).
Verdict: Good. This is the strongest result of the four — gradient, outline, and shadow all read as "the same font family" as the original at a glance.

3. Button with text — "Thêm bạn" → "Adicionar amigo"

Font: Lilita One (same reasoning as #2 — chunky button caption baked into the bitmap).
Method: bbox restricted to the button interior (away from the bevel border) via a near-white-OR-near-black threshold; fill = measured cream/white, outline = measured dark red-brown. Backdrop opaque (button face) → refilled with a dark brown gradient patch sampled from the strips at the very top/bottom of the interior (close to the bevel, hence dark).
Ink-density check: not reliable here — the background gradient patch itself is dark brown, which collides with the "ink = very dark OR very light" threshold used for measurement, inflating the apparent ink density (92%). Judged by eye instead.
Verdict: Good enough, with a caveat. "Adicionar amigo" (16 chars) vs "Thêm bạn" (8 chars) forced auto-fit down to 19px in a 150px-wide button — legible and on-model, but visibly tighter than the original's generous margins. This is the one kind (short buttons with much-longer PT-BR text) where a human/LLM pass to abbreviate the translation, or a rule to widen the button, would help more than better rendering code could.

4. Hall building caption (stylized, hall.swf) — Guild recruitment plate

Font: system Arial (same finding as #1).
Method: pixel scan found 4 line-bands matching the original's 4-line wrap exactly ("1 người vì mọi người," / "mọi người vì 1 người." / "Hãy gia nhập Guild" / "nào!"), left-aligned (all lines start within 1px of each other) → rendered left-aligned. Flat near-black fill, fully transparent backdrop (a≈0) → erase only, no fill patch.
Ink-density check: orig 13.2%, result 12.4% (ratio 0.94 — closest of the four, PT-BR string is a similar length to the Vietnamese).
Verdict: Good. Auto-wrap to 4 lines at 15px reproduces the original's layout almost exactly.

Font-extraction finding (affects #1 and #4)

FFDec font export (java -jar vendor/_tools/ffdec/ffdec-cli.jar -export font tools/i18n/fonts/extracted/<swf> "<swf path>") was run against hall.swf, hall_old.swf, core.swf, corei.swf, coreii.swf, roomlist.swf, gameover.swf. Only core.swf (→ Arial, chid 242) and corei.swf (→ Arial, chid 297) produced actual .ttf files; the rest (hall/hall_old's "Microsoft YaHei", corei's two CJK/Vietnamese-named fonts, coreii, roomlist, gameover) exported nothing — these are device/system-font references with no embedded glyph outlines, not something FFDec can turn into a usable TTF.

The two Arial files that did export turned out to be glyph-subset TTFs: they only contain the specific characters the original Vietnamese string used. A first render pass using fonts/extracted/core/242_Arial.ttf produced .notdef tofu boxes for most Latin letters in the new PT-BR text (not shown here; superseded by the Arial-by-name result above). Font extraction correctly identified which font family the original used (Arial) but the extracted file itself is unusable for free-form translated text — what actually works is referencing the real, fully-covered "Arial" by family name, which Windows + @napi-rs/canvas's GlobalFonts already exposes as an installed system font (confirmed via GlobalFonts.has('Arial')), no registration needed.

Practical takeaway for the real batch: extract fonts to identify family/weight/style as a reference, but render with a full-coverage font (system Arial/Tahoma/Segoe UI for "plain sans" originals, or a bundled OFL display font such as Lilita One for the chunky baked-in-bitmap captions/titles/buttons) rather than the extracted TTF itself, unless that TTF happens to already contain every PT-BR glyph needed (unlikely for a per-string subset export).

Overall conclusion

Code can do erase + render well when two things hold: (a) the text box/alignment/colors are measured from the actual pixels (not OCR, which is what made the old replace.mjs pipeline noisy), and (b) the render font is a full-glyph-coverage font chosen to match the original's look (system Arial-family for plain UI text, a bundled chunky OFL display font for baked-in titles/buttons/captions) rather than a literal FFDec-exported embedded font, which is usually either a glyph subset or not exportable at all. Flat-text captions (#1, #4) and chunky display titles (#2) come out looking native. The one weak spot is short buttons whose PT-BR translation is much longer than the Vietnamese original (#3) — auto-fit keeps it legible but cramped; that case needs either a shorter PT-BR string or a slightly enlarged button, which is a translation/layout decision, not a rendering one.
